# DSH 0.2.2 适配记录

## 0.2.2-rc.1

Sidechain 版本跟随目标宿主，更新为 `0.2.2-rc.1`。开发依赖及锁文件固定到对应官方 DSH 包，Cordis 更新为 `4.1.0`，Schemastery 更新为 `3.19.0`，重新生成发布用 `lib/`。没有修改 DSH 源码。

同一个插件包支持以下范围，包清单、插件清单和 DSH peer dependencies 保持一致：

```text
>=0.2.1-rc.2 <=0.2.1-rc.5 || 0.2.2-rc.1
```

两段范围是明确的并集，不包含未经验证的 `0.2.1` 正式版、中间版本或后续版本。Cordis peer 范围为 `4.0.5 || 4.1.0`，对应两代实测宿主。

## 接口调整

1. **等待投影注册完成。** 新版 `sessionProjections.register()` 的合同要求先等待注册，再发布消费者。插件 `apply()` 改为异步，首先等待 `sidechainModes` 就绪，再安装命令和相关生命周期逻辑。投影使用新版 `ProjectionDefinition<'sidechainModes', SidechainModes>`，删除已废弃的 `SessionProjectionStateMap` 扩展；状态结构与 `stateVersion: 2` 不变。旧宿主也已实测支持这一加载流程。
2. **按完整图片引用读取附件。** 新版 `SessionAttachmentRequest` 需要 `attachment: ImageAttachmentRef`，宿主会校验格式、字节长度和尺寸。侧栏传入日志中的完整引用，同时保留旧宿主所需的 `attachmentId`。官方普通 RPC 编解码会移除未知字段，新旧宿主分别消费自己认识的字段；没有添加运行时版本判断或失败重试分支。
3. **对齐真实工具执行测试。** DSH 已将单次工具执行入口迁移至批处理 pipeline；原有权限测试改用官方 `executeToolBatch`，继续验证禁止工具、子会话本地工具、卸载重载和父会话不受影响。插件的工具限制实现无需改变。

投影就绪和图片读取的回归用例均先观察到旧实现失败，再验证修复通过。两个 TypeScript 检查及 Host/Client 构建通过；原有完整测试运行加修复后的受影响文件复测，合计 128 项用例全部通过。

## 真实浏览器验证

2026-11-05 将同一个打包产物通过各版本官方 CLI 安装到五个独立 DSH home。`0.2.2-rc.1` 使用本机已安装的官方 CLI，旧版本使用 npm 官方包。逐一核对实际 CLI、Session、Subagent 和 LLM 包版本；五份已安装插件的 Host/Client 产物 SHA-256 与当前仓库 `lib/` 完全一致。旁边的 DSH 源码为 `66491b05e3`，标签 `dsh-v0.2.2-rc.1`，保持干净。

- 五版 `/btw` 均继承父代号，侧栏没有续聊输入框；`/side` 通过真实 `read` 读取文件并在追问时记住两项信息。刷新及停止、重启实际宿主进程后，BTW 身份和历史仍正确，SIDE 可继续真实模型对话。父日志不包含子文件值、子回答或子代理通知。
- 冷重启时启用 `readOnlyTools: [read, grep, glob]`，五版恢复会话的模型请求均符合限制：新版只有这三个工具；旧版另显示宿主本地 `subagent`，其执行仍受插件守卫约束。在新版及 RC.2 另建受限侧会话，实际读取文件成功；父会话仍保留 `write`、`bash`。模型未调用禁用工具，拒绝执行分支由官方工具 pipeline 测试覆盖。
- 新版及 RC.2 在主输入框上传同一张 160×80 PNG，通过 `/btw` 发起真实图片问答。两版模型都识别出蓝底白字 `SIDE IMAGE`；侧栏图片解码后的宽度为 160，附件 RPC 返回成功，BTW 仍只读。由此验证完整引用和旧 ID 两种附件请求合同。
- 新版及 RC.2 捕获到带唯一标记的未完成文本，子会话仍运行时父输入框保持可编辑；最终文本完整，运行提示消失。两版另验证 `/side list` 命令身份和 DSH 原生 BTW 历史入口。

初次同时操控多个可见浏览器时，部分流程失去侧栏可见状态；没有捕获插件异常，也未定位原因。恢复现有会话后改为逐个操作浏览器，上述路径通过。图片实验首次 Enter 未真正提交，改用界面的发送按钮后通过。这些实验记录保留在本地，不将测试脚本修正描述为插件缺陷修复。

另调用五版官方 `evaluatePluginCompatibility`，上述五个版本均被接受；`0.2.1`、`0.2.1-rc.6`、`0.2.2-rc.2` 和 `0.2.2` 被拒绝。边界版本号仅作为范围检查输入，不代表确认发布或实际运行过这些版本。浏览器验证没有插件异常；仍有宿主 `/open-in-app/icon/filemanager` 的 HTTP 404。

## 证据与范围

一次性脚本、安装包、截图和真实会话记录位于忽略入库的 `dist/rc221-compatibility/`，按 `rc221`、`rc2`、`rc3`、`rc4`、`rc5` 分目录保存。每版包含 `versions.json`、`results.json`、`side-tool-real.png`、`cold-btw-real.png`、`final-real-browser.png`；新版和 RC.2 另有 `image-real.png`、`stream-real.png`、`readonly-real.png`。本地启动信息包含认证信息，不应发布原始 `ready.json`、浏览器存储状态或宿主日志。

五个宿主使用独立数据目录，不代表旧宿主可以读取新版写入的数据，也未覆盖旧数据跨版本迁移、Electron、PTC 实际模型调用或 #11 的长历史场景。本次不改变 #5 的完成回合继承限制。历史问题分析仍见 [0.2.1 记录](dsh-0.2.1-compatibility.md)。

市场索引固定到已提交源码。发布时先提交源码及 `lib/`，再运行 `pnpm build:market` 并提交、推送生成的索引；版本、兼容范围和安装 SHA 均从该源码提交派生。
